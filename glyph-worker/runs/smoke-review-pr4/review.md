## Summary (2-4 sentences)

This is a tight, security-first addition: Mode B (local eve + ngrok) for SMS (Twilio), Slack (own app), and Email (Resend), plus a shared connector-kit with signature verification, dedupe, retries/alerts, and a launch gate. The "verify before parse", allowlists, Svix/Twilio/Slack v0 checks, SQLite dedupe, and the email threading/idempotency are generally correct. However there are a few concrete security/correctness gaps (subdomain boundary in email `addressedTo`, potential bypass of the "addressed to inbound domain" check by multiple `To` entries, and a minor Svix base64 handling detail) plus one small runtime guard for the agent model base URL. Treat those before merging.

## Findings

1. [high] connectors/email-resend/handlers.ts:12-16: `addressedTo` uses `endsWith("@" + d)`. That accepts addresses like `agent@notin.example.com` only if we compare the full domain, but also `foo@in.example.com.evil.example` would be rejected? Also `a@sub.in.example.com` is allowed only if `d` is exactly `sub.in.example.com`. However if `TARX_EMAIL_INBOUND_DOMAIN` is set to a parent domain by mistake, or if a message has multiple `To` values and any single one passes, the check is "any match" which is intended. The real issue: `x@evil-in.example.com` test shows awareness, but `endsWith` is a suffix match against the local-part+domain string; better to compare the domain part only (split on last `@`) to avoid accidental acceptance if someone ever passes a bare domain in a weird form. Also treat case-insensitively for the domain.  
   Fix: `function addressedTo(email:{to?:string[]|null}, domain:string|undefined){ const d=(domain??"").trim().toLowerCase(); if(!d)return true; return (email.to??[]).some(t=>{const a=addressOf(t).toLowerCase(); const at=a.lastIndexOf("@"); if(at<0)return false; return a.slice(at+1)===d; }); }`

3. [med] connectors/email-resend/handlers.ts:51-56: `threadInfo` falls back to `resend:${email.id}` when no `Message-ID`, no `References`, no `In-Reply-To`. That gives a deterministic root but means two different inbound emails with no headers become the same thread token unless `email.id` differs. Also if `own` is empty string you correctly don't push it into `references`. Good. However `references = [...new Set([...refs,...inReplyTo,...(own?[own]:[])])]` keeps order by first-seen; when you later truncate to keep root + last 19, you must keep the first element (root). Your `replyHeaders` does `refs[0]` + slice(-19) which assumes `refs[0]` is the thread root. Since `root = refs[0]??inReplyTo[0]??...`, ensure you never overwrite root by re-ordering: build `refs` as `[root, ...others unique except root]`.  
   Fix: compute `root` first, then `const tail = [...refs,...inReplyTo,...(own?[own]:[])].filter(x=>x!==root); const references=[root,...[...new Set(tail)]];` (and cap in `replyHeaders` as you do).

7. [med] packages/connector-kit/src/sqlite-idempotency.ts:30-45: `claimStmt` is `INSERT ...
